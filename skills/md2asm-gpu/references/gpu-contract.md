# GPU execution contract

Revision 1.3 extends GitHub main `6536b88572b8c3970361849342d7355a3440900f` to NVIDIA GH200 GPUs. The [shallow-water](../../md2asm/references/shallow_water.md) and [energy-balance](../../md2asm/references/budyko_sellers.md) numerical contracts remain authoritative for their equations, ordered FP64 operations, supported shapes, stability limits, canonical bytes, and independent physical checks. This reference changes the execution target and records how the same calculations run in parallel; it does not change the science.

## Target and arithmetic

The initial target is one NVIDIA GH200 with compute capability 9.0, Linux on little-endian AArch64, CUDA 12.6, PTX 8.5, and an `sm_90` cubin. A cubin stores the machine instructions assembled from PTX. Handwritten assembly uses explicit nearest-even FP64 arithmetic, correctly rounded division and square root, bit-preserving copies, and no flush-to-zero. The original CPU Fortran reference runs with FPCR=0 and contraction disabled. Language controls must meet the same arithmetic rules; tensor cores, reduced precision, approximate arithmetic, reassociation, and fused model multiply-add operations are excluded.

GPU entry arguments are unsigned 32-bit dimensions and stage selectors plus unsigned 64-bit device addresses. All numerical arrays remain disjoint and at least 8-byte aligned, with the exact CPU layouts: shallow-water states contain `3*(nx+2)*(ny+2)` values and scratch contains five fields; energy-balance states and scratch contain `n+2` values and coefficients contain three fields. Parameters retain their original byte order. Threads with indices beyond the declared work range return before reading or writing numerical arrays. GPU registers are private to a thread and need no host-register preservation; any shared storage and barrier requirements belong to the entry's documented launch contract.

The host may allocate, transfer, launch, synchronise, capture graphs, and write returned bytes. Every flux, wave speed, stage update, periodic copy, and pole copy runs in the declared GPU source. Independent cells may be scheduled freely because neither model has a reduction inside its time step. Reductions used for scientific checks stay outside the timer in the inherited deterministic evaluator.

## Complete stage sequence

The vanilla shallow-water sequence is input halo, D03 point preparation, D04 component update, stage halo, D03 preparation, D04 final update, and output halo. A halo thread copies each face or corner directly from its corresponding interior cell so that no ghost depends on another concurrent ghost write. Preparation reads only after the preceding halo launch has completed. One component-update thread computes all four faces for one cell and component, following the fixed arithmetic order and left-speed tie rule.

The vanilla energy-balance sequence is input pole copies, D02 faces, D03 first update, stage pole copies, D02 faces, D03 final update, and output pole copies. Pole faces are explicitly positive zero; temperature equal to the threshold selects ice forcing. A fused cell kernel may recompute the same rounded neighbouring face values instead of storing them, provided that all operands and rounding points agree and returned stages remain complete.

All launches use one ordered CUDA stream; its launch boundaries supply whole-grid producer/consumer ordering. Different blocks do not synchronise through a block barrier. An optimised entry may read periodic neighbours directly and write each output ghost from the exact same completed interior result, or use other fusion, only after proving the same stage dependencies and validating every returned bit.

For the first fused shallow-water schedule, point preparation reads the wrapped interior for every ghost location and writes that input ghost itself. Its diagnostic values therefore use exactly the same bits as the separate halo sequence, and no thread reads a concurrently written ghost. Each cell-update thread also writes its own output to the corresponding ghost locations when it lies on a boundary. Each ghost has exactly one interior source, including corners and one-cell dimensions, so these stores neither race nor require a new numerical calculation. Two preparation launches and two update launches complete a step.

The aggressive shallow-water schedule first copies `3*(2*(nx+2)+2*ny)` periodic edge values before a nonempty batch. Preparation then reads each location directly, including its ready ghosts. Every update stores the complete interior and its corresponding output ghosts, so all later preparations have ready boundaries without another halo launch. At up to 4096 cells, one thread computes one field and the update grid has three z planes. At 4097..65536 cells, the update grid uses separate x and y coordinates. Above 65536 cells, one flat-grid thread computes all three fields. The small and large schedules use 64 threads per block, and the medium schedule uses 128. The latter two cache each face's rounded half-wave-speed once outside the three-component calculation, preserving its original rounding and left-speed tie rule. `sw_prepare_clean`, `sw_edges`, `sw_update_small`, `sw_update_medium` and `sw_update` declare these routes. All updates take nx,ny,q,base,out,work,par,final in the original unsigned dimension and pointer ABI.

For the first fused energy-balance schedule, each update computes its two ordered face fluxes locally, forcing the pole faces to +0. Threads at the first and last band copy their own input value to its pole ghost and their computed output to its output ghost. All flux operands are interior values and immutable coefficients, so no consumer reads a concurrent ghost write. Two ordered update launches complete a step, and the first stage remains observable.

The first aggressive energy-balance schedule uses `eb_persistent(n,q,stage,out,work,coeff,par,steps)` for 1..128 bands. Exactly one block of 128 threads holds three rows of 130 FP64 values in 3120 bytes of shared memory. Inactive threads still reach the initial barrier and both barriers of every step. Each active thread loads its immutable coefficients, parameters and rounded dt/C ratio once. Interior neighbours supply the first and final updates, with positive-zero pole faces. Physical shared rows, rather than only the final logical row, are copied back to q,stage,out, including pole ghosts. This preserves input-interior immutability for one step and q/out parity for repeated steps.

For the first aggressive larger energy-balance grids, `eb_complete(n,q,stage,out,work,coeff,par)` computes a cell's first stage and its neighbours' first stages from the original q values, then computes and stores its final stage. Recomputed first-stage expressions keep every original operand and rounding point. A consumer needs no value that another block is still producing. One launch with 128 threads per block completes a step, and the returned first stage and both boundary copies remain complete. The host only alternates pointers between these complete steps. These schedules preserve the physical method and every required output bit while exchanging extra arithmetic for fewer launches or memory transfers.

The further assembly schedule dispatches once on the spacing bits. A positive power of two with a finite normal inverse gives the same rounded result for division and multiplication by that exact inverse, including signed zero, gradual underflow, ties and overflow. The sign and fraction must be zero and the stored exponent must be in 1..2045, giving inverse exponent 2046 minus the original exponent. Every other divisor retains div.rn. Water takes the multiplication path only when both spacings qualify, with the original component method, stages and boundaries. It inlines its own rounded face calculation. Energy balance dispatches before the entire repeated loop, avoiding a fallback decision at each division. The actual cubins expose division_check for independent CPU edge-value checks of the same inverse construction and rounded arithmetic. No approximate reciprocal or new intermediate rounding is introduced.

The further small-grid energy-balance entry keeps each band's current temperature in registers and uses two shared rows of 130 FP64 values, totalling 2080 bytes. Its two stages are unrolled. Every thread reaches the initial barrier and two barriers per complete step, including inactive threads. The last preceding state, first stage and final state restore both physical q/out rows and all pole copies according to the complete step count.

Above 128 bands, eb_temporal(n,q,stage,out,work,coeff,par,steps) launches exactly 128 threads in each of ceil(n/112) blocks, with at most four complete steps per call. Each block owns 112 consecutive bands and initially loads eight extra bands on each side. The global index is 112 times the block index plus the local thread index minus 7, with local indices starting at zero. Only global interior bands load state and coefficients. At step k, starting at zero, the first stage uses local indices from 2k+1 through 126-2k and the final stage uses 2k+2 through 125-2k. Each stage has a block barrier. Thus all owned local indices 8..119 have every required neighbour through four complete steps. Physical pole faces remain positive zero. Two shared rows of 128 values use 2048 bytes.

Only owned threads return the last preceding state to out, the last first stage to stage and the last final state to work, with unique pole owners. This tile kernel never writes global q. The ordered eb_publish(n,q,out,work,steps) kernel then restores the required physical rows, using 128 threads per block. For an even batch q receives work and out retains the preceding state. For an odd batch q receives the preceding out value and out receives work. Publication begins only after every tile has finished reading the immutable original q. All full batches contain four steps, so q remains the next input; an optional final remainder preserves total odd/even parity. Both required returned stages remain complete and scratch contents remain unspecified as in the frozen contract. No block reads another block's newly produced state during a tile batch.

The previous assembly baseline is frozen in commit 8c302c8 and built with make gpu-prelead. The first pass remains commit 2ef5dc5. Both baselines and the unchanged vanilla and tuned language controls use their original numerical code. Accepted paired measurements compare the final assembly with each baseline on shared guarded arrays. Scientific and graph cases also cover the 112-band ownership boundary, partial tiles and multiple four-step batches with odd and even remainders.

The current scheduler devices use one compute process per GPU. Evaluate native and compiled Python variants together within one process, and each Julia variant in a separate sequential process on the same GPU UUID. The parent supervising a Julia worker must not hold a CUDA context. Rotate these process groups across repetitions and disclose their separate allocations and startup costs. Do not substitute a different GPU for a language control.

Repeated execution alternates `q` and `out`: the last state is `out` for an odd count and `q` for an even count, while `stage` stores the last first stage. Zero steps launch no numerical operation and leave every buffer unchanged. Ordinary execution and CUDA graph replay must obey the same rule. Graph capture records a fixed sequence of already compiled launches and does not compute numerical values on the host.

## Verification and timing

The unchanged CPU vanilla Fortran solver is the canonical discrete reference. Reuse every inherited independent physical case, stage trajectory, boundary and input check, guard check, repeated-entry check, and canonical file comparison. The acceptance limit for raw states and files is zero differing bytes. A mismatch report includes the first case, step, stage, component, cell, and both unsigned 64-bit values.

Primary workloads retain shallow water at 64², 256², and 1024² cells with 256,128,32 complete steps, and energy balance at 128,4096,65536 bands with 512,256,128 steps. Timing includes both stages and boundaries of each complete step on one fixed GPU, measured by same-stream GPU events after warm-up. The primary display unit is million complete cell updates per second, as in the CPU plots. A shallow-water update includes all three fields and both stages, and a band update includes both energy-balance stages. Graph construction, allocation, compilation, transfers, file output, and verification stay outside that interval, with their separate costs recorded. Step counts remain within the inherited one-million-step domain and use identical inputs and counts for all controls at a workload.
