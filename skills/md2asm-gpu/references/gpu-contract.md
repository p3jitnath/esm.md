# GPU execution contract

Revision 1.1 extends GitHub main `6536b88572b8c3970361849342d7355a3440900f` to NVIDIA GH200 GPUs. The [shallow-water](../../md2asm/references/shallow_water.md) and [energy-balance](../../md2asm/references/budyko_sellers.md) numerical contracts remain authoritative for their equations, ordered FP64 operations, supported shapes, stability limits, canonical bytes, and independent physical checks. This reference changes the execution target and records how the same calculations run in parallel; it does not change the science.

## Target and arithmetic

The initial target is one NVIDIA GH200 with compute capability 9.0, Linux on little-endian AArch64, CUDA 12.6, PTX 8.5, and an `sm_90` cubin. A cubin stores the machine instructions assembled from PTX. Handwritten assembly uses explicit nearest-even FP64 arithmetic, correctly rounded division and square root, bit-preserving copies, and no flush-to-zero. The original CPU Fortran reference runs with FPCR=0 and contraction disabled. Language controls must meet the same arithmetic rules; tensor cores, reduced precision, approximate arithmetic, reassociation, and fused model multiply-add operations are excluded.

GPU entry arguments are unsigned 32-bit dimensions and stage selectors plus unsigned 64-bit device addresses. All numerical arrays remain disjoint and at least 8-byte aligned, with the exact CPU layouts: shallow-water states contain `3*(nx+2)*(ny+2)` values and scratch contains five fields; energy-balance states and scratch contain `n+2` values and coefficients contain three fields. Parameters retain their original byte order. Threads with indices beyond the declared work range return before reading or writing numerical arrays. GPU registers are private to a thread and need no host-register preservation; any shared storage and barrier requirements belong to the entry's documented launch contract.

The host may allocate, transfer, launch, synchronise, capture graphs, and write returned bytes. Every flux, wave speed, stage update, periodic copy, and pole copy runs in the declared GPU source. Independent cells may be scheduled freely because neither model has a reduction inside its time step. Reductions used for scientific checks stay outside the timer in the inherited deterministic evaluator.

## Complete stage sequence

The vanilla shallow-water sequence is input halo, D03 point preparation, D04 component update, stage halo, D03 preparation, D04 final update, and output halo. A halo thread copies each face or corner directly from its corresponding interior cell so that no ghost depends on another concurrent ghost write. Preparation reads only after the preceding halo launch has completed. One component-update thread computes all four faces for one cell and component, following the fixed arithmetic order and left-speed tie rule.

The vanilla energy-balance sequence is input pole copies, D02 faces, D03 first update, stage pole copies, D02 faces, D03 final update, and output pole copies. Pole faces are explicitly positive zero; temperature equal to the threshold selects ice forcing. A fused cell kernel may recompute the same rounded neighbouring face values instead of storing them, provided that all operands and rounding points agree and returned stages remain complete.

All launches use one ordered CUDA stream; its launch boundaries supply whole-grid producer/consumer ordering. Different blocks do not synchronise through a block barrier. An optimised entry may read periodic neighbours directly and write each output ghost from the exact same completed interior result, or use other fusion, only after proving the same stage dependencies and validating every returned bit.

For the fused shallow-water schedule, point preparation reads the wrapped interior for every ghost location and writes that input ghost itself. Its diagnostic values therefore use exactly the same bits as the separate halo sequence, and no thread reads a concurrently written ghost. Each cell-update thread also writes its own output to the corresponding ghost locations when it lies on a boundary. Each ghost has exactly one interior source, including corners and one-cell dimensions, so these stores neither race nor require a new numerical calculation. Two preparation launches and two update launches complete a step.

For the fused energy-balance schedule, each update computes its two ordered face fluxes locally, forcing the pole faces to +0. Threads at the first and last band copy their own input value to its pole ghost and their computed output to its output ghost. All flux operands are interior values and immutable coefficients, so no consumer reads a concurrent ghost write. Two ordered update launches complete a step, and the first stage remains observable. These schedules preserve the physical method and every rounding point while removing scratch or launch work.

The current scheduler devices use one compute process per GPU. Evaluate native and compiled Python variants together within one process, and each Julia variant in a separate sequential process on the same GPU UUID. The parent supervising a Julia worker must not hold a CUDA context. Rotate these process groups across repetitions and disclose their separate allocations and startup costs. Do not substitute a different GPU for a language control.

Repeated execution alternates `q` and `out`: the last state is `out` for an odd count and `q` for an even count, while `stage` stores the last first stage. Zero steps launch no numerical operation and leave every buffer unchanged. Ordinary execution and CUDA graph replay must obey the same rule. Graph capture records a fixed sequence of already compiled launches and does not compute numerical values on the host.

## Verification and timing

The unchanged CPU vanilla Fortran solver is the canonical discrete reference. Reuse every inherited independent physical case, stage trajectory, boundary and input check, guard check, repeated-entry check, and canonical file comparison. Add only cases needed for GPU partial blocks, fusion boundaries, graph replay, arithmetic underflow or threshold paths, and supported dispatch decisions. The acceptance limit for raw states and files is zero differing bytes. A mismatch report includes the first case, step, stage, component, cell, and both unsigned 64-bit values.

Primary workloads retain shallow water at 64², 256², and 1024² cells and energy balance at 128, 4096, and 65536 bands. Timing includes both stages and boundaries of each complete step on one fixed GPU, measured by same-stream GPU events after warm-up. Graph construction, allocation, compilation, transfers, file output, and verification stay outside that interval, with their separate costs recorded. Step counts remain within the inherited one-million-step domain and use identical inputs and counts for all controls at a workload. Every timed last stage and final state is compared with the original reference outside timing.

Reserve an exclusive Slurm node, record the live job and node identity, use fixed host affinity and GPU UUID, and require an idle selected GPU with no foreign compute process before warm-up. Record CPU load and foreign activity, GPU clocks, utilisation, power, temperature, memory, and throttling where available before and after a batch. Reject a disturbed batch. Rotate implementation order across at least twelve final repetitions and report the median, dispersion, minimum, maximum, and paired tuning gains. Native comparisons reuse the same buffers; disclose separate Julia process placement and its variation.

## Observable generation and evidence

The direct route is Markdown equations and frozen ordered contract, then LLM-emitted `solver.ptx`, then `ptxas`, then a cubin loaded by the CUDA driver. GPU Fortran, Julia, and Python controls follow their normal compiler routes and do not supply source or intermediate code to the direct solver. Record source and binary hashes, build commands and versions, actual GPU identity, failures, instruction audits, verification results, and repeated timings. Claims apply only to the declared models, inputs, device, and measured conditions.
