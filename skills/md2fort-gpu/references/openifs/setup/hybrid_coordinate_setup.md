# Complete Hybrid Coordinate Setup on the GPU

The [scientific contract](../../../../md2fort/references/openifs/setup/hybrid_coordinate_storage.md) defines the unchanged equations, interface and accepted domain.

An owner is a complete allocated buffer. A stride gives the distance between neighbouring stored values. FP64 is the 64-bit floating-point format. The application binary interface, or ABI, fixes argument registers and the registers that a call must preserve. The [GPU calling rules](../gpu_call_context.md) define the shared context and status fields.


This GPU implementation changes the numerical loops of the accepted hybrid-coordinate constructor. It keeps the input selection, all guards, eight allocations, complete descriptors, allocation-failure cleanup and release function unchanged. The existing scientific contract is linked below. The live coefficient arrays remain inputs. The level count N remains zero through 256, and the positive reference pressure P0 remains a live FP64 value in pascals.

The parent owns a fresh 512-byte descriptor record and the eight original output allocations. Readonly A and B each contain N+1 FP64 words and may alias each other under the existing contract. A is measured in pascals and B is dimensionless. The parent validates them before allocating. The first source loop copies both coefficient words before dividing A by P0. The second loop retains the two separately rounded products and subtraction for the cross coefficient, the separately rounded sums and half-products for layer means, then both layer differences. Their exact order is the order in the accepted source. The two unwritten full-level words at index zero and all three minimum empty owners retain their incoming bits.

One owning GPU thread executes the complete two-loop calculation. The existing four qualified IEEE FP64 status functions supply separately rounded add, subtract, multiply and divide operations. Every returned flag is consumed immediately and combined with bitwise OR. These functions add no errno event or source call counter. The Arm parent retains all public counters at their original boundaries. The host phase restores the incoming errno and floating-point control, then combines the GPU flags with the incoming sticky flags. No high-level numerical code or original OpenIFS routine supplies the candidate calculation.

The private host entry receives the record in x0, N in w1, A in x2, B in x3 and P0 in d0 after the unchanged successful allocation stage. It passes a 40-byte five-word input record and an independent 64-byte status context to one ordinary GPU launch. Both records remain live and eight-byte aligned until synchronisation completes. The status context contains error32 at byte zero, revision one at byte four and new numerical flags32 at byte eight. The remaining words start at zero, and success writes one to the completion word at byte twenty-four. The host preserves x18, all required Arm saved registers, stack alignment, FPCR and errno. It explicitly prepares the ordinary CUDA runtime before the launch, including a first cold call. A transport failure terminates the candidate rather than returning a fabricated successful state.

The GPU entry accepts one block, one thread and no dynamic shared memory. The input record contains the descriptor address, zero-extended N, A address, B address and raw P0 word at offsets zero, eight, sixteen, twenty-four and thirty-two. The private caller supplies all original buffer bounds and disjointness guarantees. Shape and context failures set the error word before numerical writes. The complete source parent still returns zero for success, one after original allocation-failure cleanup or two for original prewrite rejection.

Component checks compare complete owners, including padding and status, with retained original records. Existing independent physical checks remain applicable to the unchanged equations. The exact component records stay local. Complete forecast acceptance and its wall-time comparison remain separate.
