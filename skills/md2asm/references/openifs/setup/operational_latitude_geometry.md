# Operational latitude geometry

This component implements the complete selected `SULEGA` calculation for 2,560 physical rows and two halo rows at each pole. A halo row is an extra row that supports calculations near a boundary. The existing [32-row component](latitude_geometry_setup.md) stays unchanged. The new assembly uses public `TRANS_INQ` to obtain Gaussian latitudes and weights, then owns the calculations, storage, pole extension and release. The original OpenIFS routine is used only in a separate reference process.

## Interface and storage

`md2asm_initialize_operational_latitude_geometry` receives a writable 640-byte latitude record in `x0`, a read-only 352-byte dimension record in `x1`, and two read-only FP64 constants in `x2`. The constants are Earth radius 6,371,229 metres and pi with raw word `0x400921fb54442d18`. The result in `w0` is 0 for success, 1 for an allocation failure and 2 for a refused input. The release entry `md2asm_release_operational_latitude_geometry` receives the latitude record in `x0` and clears its nine owned pointers after freeing them.

Each record must be aligned to eight bytes, mapped for its complete extent, nonwrapping and disjoint from the other records. The floating-point control register must be zero. The dimension record supplies `NDGLG=2560` at byte 0, `NDGSUR=2` at byte 12, `NDGSAG=-1` at byte 16, `NDGENG=2562` at byte 32 and a live positive public-transform handle `NRESOL` at byte 296. The nine output pointers at bytes 0, 64, ..., 512 must start null. The inactive `RLATI` descriptor at bytes 576 through 639 keeps its complete incoming bytes.

The record holds nine GNU Fortran 12 rank-one descriptors, each 64 bytes. `RW` owns 2,560 FP64 weights with indices 1 through 2560 and occupies 20,480 bytes. Each remaining owner, `RMU`, `R1MU2`, `R1MUI`, `R1MUA`, `RSQM2`, `R1QM2`, `RACTHE` and `RLATIG`, holds 2,564 FP64 words with indices -1 through 2562 and occupies 20,512 bytes. In that order, the eight row arrays store latitude sine, squared cosine, reciprocal squared cosine, radius-scaled reciprocal squared cosine, cosine magnitude, reciprocal cosine magnitude, radius-scaled reciprocal cosine magnitude and angle in radians. The radius-scaled reciprocals have units of inverse metres; the other values and weights are dimensionless except the angle. The total public storage is 184,576 bytes. Two private arrays each use 20,480 bytes, so peak owned data is 225,536 bytes. Every descriptor field other than its allocated address follows the original source.

The constructor frame uses 608 bytes. The accepted public-inquiry adapter uses a further 352 bytes, excluding stack used inside external libraries. The release frame uses 96 bytes. Both entries preserve the required saved registers, `x18` and the low 64 bits of each used saved floating-point register. They restore the incoming error number. A failed allocation frees each acquired array once, clears its owned pointer and retains the source-defined partial descriptor fields.

## Ordered calculations

Let `mu` be a returned Gaussian latitude sine and let `R` be the Earth radius. For each physical row, the assembly computes `q = 1 - mu*mu`, calls public scalar `asin(mu)` for the latitude angle, then forms `1/q`, `sqrt(q)`, `1/sqrt(q)`, `1/(R*q)` and `1/(R*sqrt(q))`. Each multiplication, subtraction, division and square root rounds separately to FP64. The assembly preserves the original numerical dependencies and public-call boundary. It uses no fused operation, contraction, reassociation or reduced precision.

The public inquiry receives the live handle at optional-argument slot 0, the complete private latitude descriptor at slot 40 and the weight descriptor at slot 41. The other optional arguments are absent. The assembly follows the original eleven-allocation order, frees the private latitude sine array after the physical rows, then copies the seven non-angle fields into the four halo rows. Northern angles use `pi - phi`; southern angles use `-pi - phi`. The private angle array is freed after those calculations. Public Gaussian weights retain the provider's half-integral normalization, so their sum is one.

## Checks and limits

The genuine source and assembly ran in separate bounded processes. Two complete allocation preimages produced zero differing bytes across all 369,152 returned owner bytes. The checks also compared the complete records, dimensions, constants, guards, inactive descriptor and released record under 18 explicit owner-address correspondences. Seven native ABI observations passed. Failures at allocation attempts 1 and 11 and a 2,558-row refusal preserved the required status, metadata and cleanup behavior. Source and native FPCR, FPSR and error numbers agreed; the original source's known `x18` change was recorded separately from the native requirement to preserve it.

Independent checks covered all 2,564 latitude rows, 10,256 reciprocal and radius relations, 28 mirrored field relations, the four extended angles and all 2,560 positive weights. The cosine check derives a bound for each row from exact binary input values, separate multiply/subtract/square-root rounding and the greater sensitivity near a pole. Outward high-precision intervals independently bound the public inverse angle and the halo subtractions. The original fixed cosine tolerance failed near a pole and remains in the local record; no source or assembly rerun was needed to check the corrected mathematical bound.

The assembly has no original OpenIFS numerical dependency. Public transforms, scalar `asin`, allocation and the required public language runtime remain external services. This checkpoint reuses the accepted live transform setup. It does not qualify a new transform, a direct Gaussian solver, `SUMP`, the complete horizontal setup, initial grid-point loading or an operational forecast.
