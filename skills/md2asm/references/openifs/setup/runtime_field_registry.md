# Runtime field registry

A field registry records names, addresses and array dimensions so that later calculations can find their inputs. This component constructs metadata only. It does not calculate weather values. The checked route uses newly constructed MODEL, FIELDS, configuration and surface metadata owners, 21 accepted radiation owners and 66 explicitly supplied numerical input arrays. Its 20,400-byte Geometry-shaped input is a declared storage fixture. It is not complete physical Geometry or loaded weather.

`md2asm_prepare_runtime_field_registry` receives the Geometry storage address in x0, the 529,288-byte FIELDS address in x1, the 4,275,088-byte MODEL address in x2 and a writable four-byte result address in x3. Records and pointer slots require eight-byte alignment, and the result requires four-byte alignment. Every complete record, descriptor and referenced input span must be live, mapped, nonwrapping and separate from mutable outputs. These are raw caller prerequisites; the entry does not validate every address range. The result is zero when the registry is ready, one when FIELDS refers to a different MODEL and two after a metadata allocation failure. Register x0 is incidental on return. The existing already-ready check precedes the MODEL relation check. A partial failure leaves earlier owners live for caller cleanup.

The parent calls INIT, REGISTER_GEOMETRY, REGISTER_GMV_FIELDS, REGISTER_GFL_FIELDS, REGISTER_SURFACE_FIELDS, REGISTER_EC_PHYS_FIELDS and REGISTER_PHYSICS_RADIATION_FIELDS in that source order. It reads block width and block count from live Geometry metadata. Field dimensions, strides and component indices come from the supplied descriptors and actual metadata producers. The checked parent profiles have width 17, 137 levels and either one or seven blocks. They do not establish another complete parent shape. The unchanged leaf bounds and layouts are described in [Registry Storage Children](field_registry.md).

The lease first calls the accepted selected MODEL and initial FIELDS constructors. The accepted configuration constructor then reads the retained initial headers and actual namelist text and creates the GFL components, GMV index maps and configuration record. The accepted surface constructor uses those actual controls. The caller supplies 21 Geometry arrays, four GMV arrays, two GFL arrays, 34 surface arrays and five ECMWF physics arrays as explicit component inputs. The accepted radiation control and storage entries create the 21 selected radiation owners. EMTU and RMOON remain correctly unallocated. This route copies no captured process pointer and changes no MODEL control to fit a prepared fixture.

PTR is a field pointer, and DATA is the field's allocated storage. The runtime surface method changes only empty embedded group assignments. The original assignment returns separate PTR and DATA owners. In the retained original code, its second constructor evaluation supplies PTR, and a later independent constructor evaluation supplies the bytes copied into DATA. The runtime child preserves that relationship. It constructs PTR with the unchanged allocation child, allocates a distinct DATA destination, allocates a private source, copies the complete logical byte span with `memcpy` and releases the private source. It does not initialize a physical value. The two returned owners remain distinct and live for the metadata lifetime. A later numerical stage must define each temporary before reading it.

`md2asm_registry_allocate_runtime_surface_group` receives a complete 328-byte or 400-byte FIELD in x0, a signed 32-bit shape vector in x1, rank three or four, meaning three or four array dimensions, by value in x2 and thread-buffer flag one in x3. The shape must have nonnegative extents and an eight-byte element product that fits the allocation and pointer bounds. Zero logical bytes still require a one-byte allocation. The result is w0 zero for success or one for allocation failure. A failure at the first allocation preserves the field preimage. Failure at the second retains the first PTR owner and the existing single-owner partial state. Failure at the third retains the separate PTR and DATA owners. No atomic rollback is claimed. A caller that retires the returned graph must release both distinct reachable payloads exactly once; this component adds no production finalizer.

The source-defined metadata comparison retains complete names, codes, flags, rebuilt PTR descriptors, allocated DATA descriptors, associated array descriptors and typed pointer identities, offsets and aliases. A null FIELD VIEW or unallocated DATA descriptor defines its eight-byte base; its other descriptor words are undefined by the source constructor. The same rule applies to each unassociated VARIABLE public view and absent variable-array descriptor. The runtime retains the accepted deterministic zero representation in those undefined words. Rebuilt PTR descriptors remain fully compared, including their complete headers for the unassociated EMTU and RMOON inputs. Numerical output bits are never rounded, repaired or masked.

The exact undefined ranges below are relative to the start of each null descriptor. Its base bytes 0–7 remain compared. No range in an associated descriptor is excluded.

| Null descriptor | Full descriptor bytes | Undefined bytes |
| --- | --- | --- |
| FIELD VIEW, field rank 2, 3 or 4 | 64, 88 or 112 | 8–63, 8–87 or 8–111 |
| FIELD DATA, field rank 2, 3 or 4 | 88, 112 or 136 | 8–87, 8–111 or 8–135 |
| VARIABLE public view, variable rank 2, 3 or 4 | 64, 88 or 112 | 8–63, 8–87 or 8–111 |
| Variable-array descriptor, descriptor rank 1 or 2 | 64 or 88 | 8–63 or 8–87 |

Two genuine source and native registry pairs pass at the checked block counts. Each route compares 322,449 source-defined metadata bytes per case, 10,782 typed pointer relations and 2,183 reachable owners, including all ten separate PTR/DATA group pairs. All 66 caller numerical buffers remain read-only. The complete supplied caller and radiation payloads remain unchanged, including their declared zero-extent reservations. Geometry, MODEL and the preserved FIELDS prefix remain byte-identical. Geometry, caller buffers and the result use opposite protected placements across the two cases; heap metadata and constructor records have inaccessible outer pages and complete padding checks.

The original source also leaves 70 unreachable FIELD objects and 60 unreachable payloads, totaling 33,640 bytes per case. Their complete records and allocation inventory remain local. The comparison accounts for these separately from the returned graph and releases every observed owner through verification-only cleanup. Allocation ordinals and unreachable compiler temporaries are not declared outputs. No production cleanup or complete startup claim follows from that observer.

The new child passes two success cases with different allocation preimages. DATA equals the independent third allocation's bytes and differs from PTR's bytes, which checks the copy dependency directly. Its three allocation-failure positions pass partial-state, buffer, status and cleanup checks. The complete original default parent and surface-method objects remain byte-identical, and the runtime entries reuse their bodies through assembly inclusion. Other accepted metadata children remain unchanged.

The application binary interface (ABI) defines the register and stack rules. The native ABI checks preserve x18, x19–x29, d8–d15 and the stack pointer, with sixteen-byte stack alignment. The original control has the known x18 mask two; the native mask is zero. FPCR controls floating-point operations, FPSR records their status flags, and errno is the C library error word. Both nominal routes retain FPCR zero, FPSR 24 and errno 777. Injected allocation failures return the natural ENOMEM value, which reports an allocation failure. The three new entries use only direct assembly children and public C `malloc`, `memcpy` and `free`. No original OpenIFS routine supplies a production stage, and the main Fortran executable was not rebuilt.

This component does not accept FIELD_VARIABLES update or cloning, local physics state and work arrays, cloud-budget accumulation, current-step publication, complete SUECRAD, CALLPAR, loaded weather or a forecast. The full CALLPAR integration must retain the actual cloud-budget accumulation control and its live owners, the source-selected radiation controls and the typed four-byte current-step owner.
